# Release

Releases are made by release-please from the conventional commit titles on `main`. Versions follow Semantic Versioning, and from 1.0.0 every release is a minor or a patch release of 1.x, under the promise [Getting started](../user/getting-started.md#versions) states. The commit type decides the bump: a `feat` title makes a minor release and a `fix` or `perf` title a patch release. A breaking change does not ship: the pull request title check refuses a `!` title and a `BREAKING CHANGE:` footer at 1.x. Tags are `vX.Y.Z`.

## Steps

1. release-please keeps a draft pull request titled `chore: release X.Y.Z` open. It moves the version between the markers in `include/maul-ui/base.h`, where CMake reads it and from which `MUI_ABI_VERSION` follows, updates `.release-please-manifest.json`, and adds an entry to `CHANGELOG.md` from the `feat`, `fix` and `perf` titles.
2. Rewrite that entry in user language before merging: what changed for someone using the library, grouped as Added, Changed, Fixed, Removed and Security, with the part first where a change is one part's (the text component, an accessibility adapter, the renderer, the window glue). Leave out refactors, tests, CI and documentation. Say which results change, for a minor release that changes them, and what a program changes for `maul-ui-rhi` or `maul-ui-window`.
3. Check that the `required` CI job passed on the release pull request, including every platform cell, and that the wasm sizes are within their ceilings.
4. Mark the pull request ready and merge it. release-please tags the merge commit and publishes the GitHub release with the changelog entry as its notes. The Pages workflow publishes the documentation from `main`.
5. The `assets` job of `.github/workflows/release.yml` attaches the source archive `maul-ui-X.Y.Z.tar.gz`, its `SHA256SUMS`, an SPDX SBOM and a build provenance attestation. A user verifies a download with `sha256sum -c SHA256SUMS` and `gh attestation verify maul-ui-X.Y.Z.tar.gz -R Rawframe-Project/maul-ui`.
6. If release-please fails to create the release (the Release app cannot create one on a commit whose workflows differ from `main`'s head), create the release for the tag by hand, then run the release workflow from `main` by hand with that tag as `tag`. The `assets` job builds, attests and attaches the files of the commit the tag names, which it checks before building. It refuses a tag that is not `vX.Y.Z`, a tag whose commit `main` does not hold, a release that already has files, and a run in which release-please created a different release. It never replaces a published file, so a run that failed after attaching some files is run again only after those files are deleted from the release by hand.

## Notes

- The ABI holds within a minor version: the shared library's `SOVERSION` is the major and minor version, the CMake package accepts the same major version at or after the one asked for, and the root creations (the root defs `base.h` names) refuse a def stamped by another minor version's headers with `mui_errorVersion`.
- Results (layouts, styles, draw-list bytes, accessibility trees, line breaks, shaped text, glyph images and motion curves) change in a minor release. A change that gives existing inputs a different result is titled `feat`, so release-please ships it as a minor release. It is titled `fix`, and ships as a patch release, only when it corrects a result to what the documentation already promised. Neither carries `!`, and the body and the release notes say what changes.
- A pin move that changes a result, or that takes a dependency's new API into Maul UI's, is titled `feat` with the scope of the part it reaches. Such a move of Maul RHI or Maul Window may change the API of `maul-ui-rhi` or `maul-ui-window`, which sit outside the promise until both reach 1.0, and its notes say what a program changes.
- The shared family files must match their canonical copies in the organization's `.github` repository before a release.
- Maul UI fetches Maul Tween, Maul Unicode, Maul RHI and Maul Window by tag (`cmake/Tween.cmake`, `cmake/Unicode.cmake`, `cmake/Rhi.cmake`, `cmake/Window.cmake`). A new release of one of them moves its pin in a pull request of its own, with the whole check green. Maul Window and Maul Unicode are the exception: Maul Window builds against Maul UI's Maul Unicode, so configuring stops when the Maul Unicode release Maul Window names differs from Maul UI's pin, and the two pins move together.
